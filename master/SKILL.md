# Design and frontend engineering

Build interfaces that communicate clearly, behave predictably and belong to their product. The work is design judgment and engineering at the same time: a decision about spacing and a decision about focus order get the same care.

If the project has a brief, the brief wins wherever it disagrees with this skill.

## Pick the mode first

| Mode | When | Start with |
|---|---|---|
| New build | Nothing exists yet | Steps 1 to 10 below, in order |
| Restyle from references | The owner has an inspiration board or reference products | Part 1, Process, inspiration intake and style identity |
| Audit and improve | A build exists and needs to get better | Part 4, Build and verify, audit procedure. Pull the latest repo first, because the owner may still be pushing |
| Build from Figma | The owner has a Figma file or frames to implement | Part 6, Figma and shadcn |
| Motion pass | Animations exist and need review or refinement | Part 7, Motion review |

Say which mode you are in at the start of the reply. If the request fits more than one, pick the closest and state the assumption.

## Working agreement

- State assumptions out loud instead of silently choosing one.
- Ask at most one question per reply, and only when the answer changes the work.
- Label every decision Decided (the owner chose it), Proposed (you suggested it, not yet confirmed) or Open. Never upgrade Proposed to Decided without a clear yes.
- Flag problems early (contrast, performance, feasibility, originality) and offer an alternative that keeps the intended feel.
- Show instead of describing when the thing is visual: render it, screenshot it, draft it.
- Do not pad. If a section has two real items, it has two.
- When the owner runs the code, give complete files or a complete patch plus exact commands, never loose fragments.
- Change one thing at a time when debugging. Park unresolved issues with what was tried, what was ruled out and the next test.
- A passing build or a sandbox screenshot shows the code is well-formed. It does not show it works in the owner's browser. Say which you verified.
- Never claim a tool, connector, skill or test was used when it was not available or not run.
- Do not grade your own output. Use something that returns a result (typecheck, build, a script, Lighthouse, a Playwright flow, the owner) and say which one.

## Workflow

1. **Understand the product and task.** Who the user is, what they are trying to finish, the core screens and flows, and the states each flow needs (initial, loading, empty, success, error, disabled, storage or network unavailable, destructive). Inspect the existing stack, components and conventions before proposing anything. A product interface leads with the task. A marketing page leads with one clear promise.
2. **Raise the ambition.** Ask what outcome sits behind the task (altitude), what the best professionals would do that was not asked for (depth), and which other fields bring useful methods (range). Record the answers as Proposed. Skip for small direct edits. Part 5, Ambition.
3. **Gather references.** Study several real products or the owner's board. Extract principles, not compositions. Method and ethics: Part 1, Process. Mobbin is optional and used only when it is actually connected.
4. **Define identity and tokens.** Name the style, set the filter keywords, then write primitives and semantic tokens. Verify contrast with `scripts/contrast.py`. Rules and the anti-generic checklist: Part 2, Foundations.
5. **Reuse before building.** Check installed libraries, shadcn/ui and Radix, and native elements (`dialog`, `details`, `form`) for standard behavior. Build custom only where the behavior or visual is specific to the product. Customize tokens, type and states so the result does not read as an untouched library. When a Figma file exists, shadcn gives the behavior and the Figma gives the look: Part 6, Figma and shadcn.
6. **Build the whole experience.** Not only the first visual state. Forms, feedback, undo, keyboard, touch, empty and failure states. Rules: Part 3, Interaction and accessibility.
7. **Review the motion.** List every animation and run the review pass. Use Emil Kowalski's skill when it is installed, the Playbook motion rules when it is not. Part 7, Motion review.
8. **Verify in a real browser.** Build, run, screenshot at several widths, exercise the flows, read the console. `scripts/check_page.py` automates the repeatable part. Procedure: Part 4, Build and verify.
9. **Hand over.** Summarize what changed and what was assumed, list files, give the exact commands to apply and push, and name the next step. Use the status block at the end of this file for long projects.
10. **Capture.** When the task was a multi-step workflow that is likely to recur, offer to turn it into a reusable skill. Save nothing without a yes. Part 8, Capture workflow.

## Rules that matter most

1. The brief and the owner's stated taste outrank any rule here.
2. One or two type families. Sentence case. No all-caps eyebrow above every heading, no single-word color or italic accent in headlines.
3. Tokens in two layers: primitives hold values, semantic tokens hold roles, components use roles only. No raw hex in components.
4. Radius, shadow and spacing come from small scales, not per-component values.
5. Spend boldness in one place. Remove one accessory before finishing.
6. Structural devices carry meaning. Number things only when they are a real sequence.
7. Text contrast 4.5:1 for body, 3:1 for large text and UI boundaries. Verify with the script, not by eye.
8. Body text at least 14px and a hard floor of 12px for tiny metadata. Form inputs 16px so iOS does not zoom.
9. Hit areas at least 44 by 44 px with no dead gaps between neighbors. Visible size and hit area are separate.
10. Every field has a label tied to it, errors appear next to the field and say how to fix it, and Enter submits a real `form`.
11. Destructive actions get confirmation or undo. Lightweight actions respond at once.
12. One orchestrated motion moment per view. Routine actions get feedback of 200 ms or less. Respect reduced motion. Never hijack scroll.
13. Real content in every state. No lorem ipsum, no placeholder-only labels.
14. Copy follows Part 9, Writing.
15. Tabular numerals on money, timers and counters.
16. Defaults when the brief is silent: US English, USD, 12-hour times. Currency and locale stay switchable where money is shown.
17. With a Figma file, shadcn supplies structure and behavior and the Figma supplies appearance. Every deviation from the Figma is listed with a reason.
18. Ambition that goes beyond the brief is Proposed until the owner says yes.

## Part 1: Process: from references to a brief

### Stages

Work in this order for a new build. Skip a stage only when its output already exists.

| Stage | Output | Done when |
|---|---|---|
| 1. Intake | Reference images or links, one line on what is loved, the project name | The owner confirms the set is complete |
| 2. Analysis | Recurring patterns, outliers, extraction notes | The owner agrees the read matches what they love |
| 3. Style identity | Name, definition, keywords, signature moves, anti-patterns | The owner approves the name and the filter |
| 4. Concept | Subject, audience, use cases, scope, reference log for the flows involved | The owner approves scope |
| 5. Content and data | Every page, section and data structure, plus the flow and state inventory | Nothing the build needs is undefined |
| 6. Tokens | CSS variables and framework mapping, plus a contrast table | A style tile renders correctly in a real browser |
| 7. Components | Spec and code per component after a reuse check | Every state exists |
| 8. Pages and flows | Routes, layouts, responsive behavior | Works at 360, 768, 1280 and 1920 px |
| 9. Motion | One signature moment plus responsive feedback | Reduced-motion mode verified |
| 10. QA | Accessibility, performance, cross-browser | The checklist in Part 4, Build and verify passes |
| 11. Case study | Written and visual story | Reads cleanly with no gaps |

For a restyle of an existing build, stages 1 to 3 still apply. For an audit, derive the style identity from what is already built, then judge the build against it.

### Starting a session

Reply first with a five-line restatement of the project, what is Decided, what is Proposed, what is Open, and the next step. Wait for corrections only when something looks wrong; otherwise state the assumption and proceed.

### Inspiration intake

- Screenshots at full size, 10 to 20 per message.
- Which project it is for.
- One line on what is loved: colors, layout, feel, lines, elements.

### Inspiration analysis

What to extract:

- **Color:** ground, hero fill, supporting colors, accents, text color, and the ranges between them.
- **Type:** how many voices (display, label, body, hand-lettered), weights, case, scale contrast.
- **Layout:** grid behavior, whitespace, alignment, composition.
- **Shape and depth:** radius, borders, outlines, shadows, texture.
- **Imagery:** illustration or photo treatment, scale relationships, filler motifs.
- **Line and graphic system:** line weights, dashes, arrows, icons.
- **Motion cues:** what could animate, even from static images.
- **Mood and content structure.**

Method:

1. List what recurs in three or more references. Those define the style.
2. List one-offs. For each, decide: ignore, borrow for one section, or adopt.
3. Write down what the owner loves in their own words and treat it as the priority filter.
4. Note the artists for credit.
5. Produce the style identity first, then the brief.

Hex values read from images are estimates. Sample them and verify contrast before they become tokens.

### Reference ethics

Boards and reference products are scaffolds. Take principles (color relationships, structure, feel) and make original decisions. Never trace, recreate or lightly rework another designer's composition, and never reproduce another product's visual identity because its layout was useful. Credit boards and artists in the case study.

### Pattern research for flows

- Study several real products for a flow before settling on a pattern.
- Compare what repeats and what varies.
- Follow the whole flow where possible: validation, loading, errors, result. A single screenshot hides all four.
- Note what changes on small screens and with touch.
- Mobbin is a good source when its connector is connected. When it is not, say so and use references that can legitimately be viewed.
- Keep a reference log in `docs/reference-log.md`: link, the pattern studied, what was taken, what was changed, why.

Questions to ask of any reference: what is the primary action and how clearly is it shown, how are content and actions prioritized, what happens before, during and after an interaction, how are errors and empty states handled, which details are essential to the task and which belong to that product's brand.

### Style identity template

- **Name:** two or three words, memorable, describes the feel.
- **Definition:** one sentence a stranger could picture.
- **Keywords:** five words that filter every decision.
- **Signature moves:** three to five things that make the style recognizable.
- **The one memorable thing:** where the boldness is spent. Everything else stays quiet.
- **Anti-patterns:** what would break the style.

### Brief template

1. Style name, definition, keywords
2. Reference analysis
3. Color: values, roles, tested contrast pairs, forbidden pairs
4. Typography: families, roles, scale, rules
5. Spacing, layout, shape
6. Imagery and iconography
7. Motion
8. Components and signature moves
9. Voice and tone, with Do and Don't examples
10. Anti-patterns
11. Token starter

Add to every brief: a decision log (Decided, Proposed, Open), a flow and state inventory, a status log, and a section for case study capture.

### Case study capture

Capture while building, because it is hard to rebuild later:

- The reference board and extraction notes
- The brief and decision log, including changes and the reason
- Early and final screenshots of the same screen
- Token setup and a component sheet
- Accessibility and performance results, with numbers
- What went wrong and how it was fixed

Structure: overview and link, role and tools, brief and audience, references and style identity, the system (tokens, type, components), key interactions, process (early versus final decisions), quality results, how the system adapts to other clients, what comes next. State facts and results. Do not oversell. Follow Part 9, Writing.

## Part 2: Foundations: tokens, type, color, layout, motion

### Token conventions

- **Two layers.** Primitives hold raw values (`--violet-600`). Semantic tokens hold roles (`--color-accent: var(--violet-600)`). Components use semantic tokens only.
- **Prefixes:** `--color-*`, `--font-*`, `--text-*`, `--space-*`, `--radius-*`, `--shadow-*`, `--ease-*`, `--dur-*`, `--z-*`.
- **Name collisions.** Before adding tokens to an existing stylesheet, list the custom properties already defined and check for overlap. Two files defining the same name as `--a: var(--b)` and `--b: var(--a)` create a cycle, and every value that depends on it silently becomes invalid.
- **Frameworks.** Map semantic tokens into the framework theme through CSS variables. With Tailwind v4, put tokens in an `@theme static` block and reset the default scales (`--color-*: initial`, and the same for text, radius and shadow) so only system values exist. No raw hex and no arbitrary values (`w-[137px]`) in components. A value needed twice becomes a token.
- **Modes.** When a project has scene or theme modes, change only the scene layer. Keep UI chrome constant so text contrast stays guaranteed.
- **Contrast table.** Every palette ships with tested text and background pairs, the ratios, and a list of forbidden pairs. Generate it with `scripts/contrast.py`.
- **Migrating an existing stylesheet.** Replace exact raw values with the matching token by script, then diff the build. Leave near matches alone until someone decides they are the same color.

### Typography

- One or two families, clearly distinct if two. A third only with a strong reason.
- Fluid scale with `clamp()`. Body line length under 70 characters. Serif body gets slightly more line height.
- Sentence case. Headings carry the hierarchy through size and weight, not through decoration.
- Weight around 500 to 700 for headings, depending on the face. Avoid very light weights at small sizes.
- `font-variant-numeric: tabular-nums` for money, timers, counters and table figures so digits do not shift.
- Inputs at 16px or larger. Add `-webkit-text-size-adjust: 100%`.
- Do not change weight on hover or selection if it shifts layout. Style `::selection` to match the palette.
- Load each family once. Subset when the payload matters, use `font-display: swap`, and keep to two or three weights per family.
- A headline can be part of the picture (banners, tags, tilted labels) as long as it stays readable.

### Color and contrast

- Roles first: ground, surface, ink, muted ink, line, accent, accent deep, soft accent, pop, status colors (danger, warning, success), night and on-night text.
- Text on any background: 4.5:1 for body, 3:1 for large text (about 24px, or 19px bold) and for UI boundaries and focus rings.
- Muted text is where most failures hide. Test it on every surface it appears on, including tinted cards.
- Status color never carries meaning alone. Pair it with text or an icon.
- Keep one accent family and at most one supporting hue unless the brief says otherwise.

### Spacing and layout

- 4px base scale: 4, 8, 12, 16, 24, 32, 48, 64, 96.
- A section rhythm token (for example `clamp(56px, 8vw, 112px)`) and one max content width, shared by header, content and footer so edges align.
- Use the framework's default breakpoints. Check 360, 768, 1280 and 1920 px.
- A layout concept goes in the brief as one sentence plus a rough wireframe.
- Cramped usually means three things at once: text below 14px, no spacing scale, and too many boxes. Fix all three.
- Tools lead with the task: the page title, then the primary action, then the data. Marketing pages lead with one promise and one action.

### Shape and depth

- Radius is a small deliberate scale (for example 10, 16, 24, pill), not a different value per component.
- Shadows are either removed on purpose or a small named set. No default grey drop shadow under every card.
- A hard offset shadow on primary buttons is a valid signature move if it is used consistently and the pressed state moves it.
- Borders and dividers exist to separate content, not to decorate.

### Imagery and icons

- One consistent icon style per project.
- Photos must show the product's world. Generic stock lifestyle photography weakens credibility, and hotlinked stock is a performance and privacy dependency. Prefer real product UI, owned imagery or illustration.
- Real text for labels. Never bake text into images.
- Decorative graphics are hidden from assistive technology and set to `pointer-events: none`.
- Open Graph and favicon assets belong to the project, not a third-party host.

### Motion

- **One orchestrated moment per view.** A single sequence beats scattered effects. No fade-and-slide-up on every section, no hover transition on every card.
- **Respond to action.** Motion that shows what changed (open, expand, confirm, insert) is welcome.
- **Ambient motion is rare.** At most one calm ambient element per view.
- **Duration ladder:** micro 120 to 180 ms, standard 240 to 320 ms, emphasis 400 to 600 ms, sequences 600 to 1600 ms.
- **Easing tokens:** standard `cubic-bezier(.2,.8,.2,1)`, pop `cubic-bezier(.34,1.56,.64,1)`.
- **Frequency decides expressiveness.** Routine actions get feedback of 200 ms or less and no flourish. Rare, meaningful moments may be expressive.
- **Proportional movement.** Presses and lifts are a few pixels or a scale near 0.96.
- **Continuity.** Things open from where they came from and close back to it.
- **Interruptible.** A scroll, tap or key press mid-transition is never trapped. Continuous gestures update the interface directly, with no easing delay.
- **Reduced motion.** `prefers-reduced-motion` removes draw-on, parallax, drift and bounces. Content still appears in its final state.
- **Performance.** Animate transform and opacity. Do not animate blur or filters on large areas. Pause offscreen loops.
- Motion never carries the only copy of information.

### Anti-generic checklist

Avoid these unless the brief demands them:

- A warm cream ground with a high-contrast serif and a terracotta accent.
- A near-black ground with a single acid-green or vermilion accent.
- A broadsheet layout: hairline rules, zero radius, dense columns.
- The SaaS card kit: identical rounded cards, one radius everywhere, the same soft shadow, gradient washes, four identical metric tiles with icon chips.
- Template chrome: tracked-out all-caps eyebrows, middle-dot meta strings, arrows appended to every button, spaced dash labels, monospace small labels, a decorative glyph repeated as a divider.
- A scrolling slogan ticker.
- Fade-and-slide-up on every section.
- Accenting one word of a headline.
- Numbered markers on content that is not a sequence.
- A hero that stacks a photo, a fake dashboard, a floating note and a sticker.

Self-critique: write the design plan, then review it against the brief. If any part reads like what you would produce for any similar page, revise it and say what changed. Before finishing, remove one accessory.

## Part 3: Interaction, states, accessibility and performance

Treat these as informed defaults. Context, task and platform decide.

### Interaction principles

- **Familiar metaphors.** Reuse patterns users can predict. A metaphor earns its place when it clarifies behavior.
- **Continuous input.** Where it fits, respond to a gesture as it happens instead of waiting for a threshold and jumping. Drag and scrub update the interface directly.
- **Interruptibility.** Motion shows momentum and direction, and never traps the user mid-transition.
- **Spatial continuity.** Show where something came from and where it went. Morphing helps only when it supports understanding.
- **Gesture intent.** A lightweight action may respond during a swipe. A destructive action waits until intent is clear, and is never easy to trigger by accident.
- **Frequency and novelty.** Frequent, low-novelty actions get minimal overhead. Expressive motion is for rare, meaningful moments.
- **Touch precision.** A finger hides what it manipulates. Offer persistent handles, previews or offset positioning for precise work, and size targets generously.
- **Scrolling and landmarks.** Never hijack scroll or route input to an unintended region. Long pages get landmarks: anchors, progress, back to top.
- **Implicit input.** Context can reduce effort. Inferred defaults must be visible, reversible and free of location or personal data unless the user chose it.
- **Fitts's law.** Important targets are large and near the thing they act on.
- **Playfulness.** Welcome where it costs nothing in clarity, accessibility or task completion. It is context-dependent, not a requirement.

### Flow and state inventory

Before building a flow, list its states: initial, loading, empty, success, error (with field-level causes), disabled, offline or storage unavailable, and any destructive step. Each state gets a design and its copy. Keep the inventory in the brief.

- **Empty states** offer the next useful action. A first run asks for the one or two facts the product needs and explains what they unlock.
- **No backend?** Use a small async data module with realistic latency and a switch that forces failures, so loading and error states are real.
- **Browser storage** is wrapped in try/catch and has a working empty state. Offer a way to export a backup when the data lives only on the device.
- **Optimistic updates** roll back with a clear message when the operation fails.

### Forms

- Every field has a visible label tied to it with `htmlFor`/`id` or by wrapping. Placeholder-only labels are not labels.
- Use a real `form` so Enter submits. Set input types, `inputMode`, `required` and `autocomplete`. Do not disable browser help for names, emails, addresses or authentication.
- Errors appear next to the field, name the field and say how to fix it. Link them with `aria-describedby` and set `aria-invalid`.
- Do not disable a submit button to signal invalid input. Show the errors.
- Block duplicate submits while a request is pending, and explain the pending state.
- Inputs are 16px or larger. Do not autofocus on touch devices. On pointer devices, focusing the first field in a dialog is a good default.
- Toggles take effect immediately when that matches their meaning.
- A disabled control is not explained by a tooltip, because disabled controls are often not focusable. Use visible helper text.

### Feedback and consequence

- Feedback appears near the action. A check beside a copy button beats a distant toast.
- Lightweight actions respond at once and offer undo. Removing an item restores it to its old position.
- Destructive or irreversible actions need confirmation, or a gesture that makes intent clear.
- Toasts that offer undo stay long enough to use (about seven seconds) and are announced to assistive technology (`role="status"`).

### Hit areas

- At least 44 by 44 px. A 24px icon still has a 44px target through padding or a transparent extension.
- Adjacent targets leave no dead gaps.
- Hover styles apply only where hover exists (`@media (hover: hover)`).
- Purely decorative overlays and glows use `pointer-events: none`.
- Do not disable text selection across a page. Disable it only on the inner text of a control when selecting it interferes.
- Remove the iOS tap highlight only where a visible pressed state replaces it.

### Accessibility floor

- WCAG 2.1 AA as the minimum.
- Visible keyboard focus on every interactive element. A 3px ring with an offset works on busy backgrounds. Never remove an outline without a replacement.
- Full keyboard operability, including sliders, maps and drag interactions. Drag always has a non-drag alternative.
- Semantic HTML first: landmarks, one `h1` per page, logical heading order, real buttons and links.
- Dialogs: prefer native `dialog` with `showModal()`, which provides focus trapping, Escape and an inert background. Label with `aria-labelledby`, restore focus to the trigger on close.
- Composite widgets follow the expected keyboard model: one tab stop, arrow keys inside, Enter to activate, Escape to close.
- Icon-only controls have an explicit accessible name.
- Meaningful images have alt text. Decorative ones have empty alt. Complex HTML or SVG illustrations get a name or are hidden.
- Interactive visuals (maps, charts) have a list or text alternative.
- Live regions announce dynamic updates (results that recalculate, toasts, counts).
- Never put interactive content inside a hover-only tooltip.
- Custom pan and zoom surfaces set `touch-action` deliberately.
- Reduced motion respected. Nothing flashes more than three times per second.
- Color alone never carries meaning.

### Performance floor

Proposed targets:

- Lighthouse mobile performance 90 or higher, accessibility 100.
- LCP under 2.5 s, CLS under 0.1, INP under 200 ms on a mid-range phone.
- Code-split routes. Marketing visitors should not download an app's charting and data libraries.
- Inline only the first-view critical assets. Lazy-load the rest.
- Large `blur()` filters, stacked drop shadows and full-screen SVG turbulence are expensive. Test on real hardware or avoid.
- `will-change` and `translateZ(0)` stay out unless a measurement shows a problem, and apply only for the length of the animation.
- For values that change every frame, write CSS variables or transforms through refs and keep React state for coarse readouts. Measure before and after.
- Pause or unmount offscreen looping animation and video.
- Measure on a production build, not only the dev server.

## Part 4: Build, audit and verify

### Code conventions

Default stack: React with TypeScript, Vite, Tailwind CSS, Git and GitHub, deployed on Vercel. Inspect the project before assuming it.

```
src/
  tokens/        CSS variables and framework mapping
  components/    UI primitives
  features/      project-specific features
  data/          typed config and content
  lib/           utilities (color, time, storage)
  routes/        pages
```

- Content and map data live in typed config, not inside components, wherever reuse is a goal.
- Browser storage is wrapped in try/catch with a working empty state.
- No raw hex or arbitrary values in components.
- ESLint and Prettier on, TypeScript strict.
- Pin dependency versions. `latest` in `package.json` makes builds unrepeatable. Commit the lockfile.
- Add a `.gitignore` (`node_modules`, `dist`, `.env*`).
- The README holds run, build and deploy steps.
- Commits: one concern each, imperative mood, named file adds rather than `git add .`.
- After any deploy, confirm the live URL actually updated before reasoning from it.
- Keep files readable. A one-line-per-function bundle of 40 KB is a maintenance cost; format it before editing.

### Reuse policy

- Check before building: installed libraries, shadcn/ui, Radix, and native elements (`dialog`, `details`, `form`) for dialogs, drawers, accordions, tabs, selects, checkboxes, switches, toasts and form fields.
- Build custom where the behavior or the visual is specific to the product.
- Customize tokens, spacing, type and states so the result does not read as an untouched library template.
- A Tailwind v4 project that resets the default scales needs adaptation. shadcn files use classes such as `text-sm` and `rounded-md` that no longer exist. Edit the copied files to the project's names, map shadcn variables (`--background`, `--primary`) onto semantic tokens, and configure `tailwind-merge` so custom names are not treated as conflicts.
- On Windows, `npx` based CLIs can fail. Install the packages directly and add the component files by hand.
- Record the choice: each component names the primitive it builds on, or the reason it is custom.
- Native `dialog` is a valid choice when no component library is installed. It avoids a dependency and gives focus trapping and Escape for free.

### Component spec (use for shared components)

```
Component: Name
Description: what it is, when to use it
Variants / Props
States: default, hover, focus, active, disabled, loading, error, empty
Responsive: behavior at 360 and 768 px
Motion: what animates, duration, easing, reduced-motion fallback
Accessibility: role, keyboard, announcements, names for icon-only controls
Hit area: visual size versus tappable size
Reuse: primitive used, or why custom
Tokens used
Do and Don't
```

Minimum set per project: button, link, input, textarea, select, checkbox and radio, card, nav, footer, badge, modal or sheet, toast, accordion, tabs, tooltip.

### Audit procedure for an existing build

1. **Sync first.** `git fetch`, then read `git log`, list branches and check which are merged into the main branch (`git branch -r --merged origin/main`). The owner may still be pushing, and screenshots may come from a different branch than the one you cloned. Say which branch you reviewed.
2. **Read.** Structure and file sizes, how many stylesheets or style layers compete, custom properties, counts of raw hex values, font sizes under 12px, radius values and shadow declarations, fonts loaded and whether they are requested twice, remote images and scripts, `package.json` pinning, README, routes, and what is bundled for which visitors.
3. **Look.** Run a production build, serve it, and screenshot at 360, 768 and 1280 px. Seed realistic data in localStorage to see the real states. Also look at the first-run and empty states.
4. **Rank findings.** Mark each as verified in a browser or read in code only. Order them:
   - Breaks the product: wrong numbers, lost data, dead flows.
   - Blocks users: contrast, labels, keyboard, focus, hit areas, zoom on iOS.
   - Weakens trust: generic stock imagery, filler copy, claims the product cannot back, inconsistent branding.
   - Polish: spacing, radius and shadow scales, motion.
5. **Report.** Start with what already holds up, then findings grouped by area, then the suggested order of work, then one question if the answer changes the work.
6. **Fix in batches**, in this order: foundation (tokens, scales, type floor, dead CSS), cuts (remove what does not earn its place), structure (page headings, first run, layouts), states and forms, logic, copy, motion.
7. **After each batch:** typecheck, build, run the flows in a browser, review screenshots, sweep the pages you did not touch for regressions.

### Verification protocol

- Install, typecheck and build before anything else.
- Serve the production build (`vite preview`) and drive it with Playwright. Seed localStorage to reach real states.
- Run `scripts/check_page.py` on each key route. Run `scripts/contrast.py` on every text and surface pair in the palette.
- Exercise each changed flow: open, validate, submit, cancel, Escape, undo, reload.
- Read the console. A clean console is a requirement.
- Treat a passing sandbox run as proof the code is well-formed. Real device checks (a real iPhone and a real Android phone) and a Lighthouse run on the deployed build remain the owner's confirmation.

Known pitfalls in sandboxes:

- Web fonts usually cannot load, so type looks tighter or wider than it will on the owner's machine. Say so.
- Do not `pkill -f` a pattern that also appears in your own command line. It kills your shell.
- Start long-running servers with `setsid nohup ... &` so they survive between commands.
- Full-page screenshots place fixed elements (bottom navigation) mid-page. Check them in a viewport screenshot.
- Changing only the hash does not reload the page. Test hash entry from a fresh load.
- Text selectors such as `button:has-text("Calendar")` can match navigation items. Scope selectors to a container.
- Prettier on a minified file produces a very large diff. Tell the owner before doing it and do it once.

### Pre-ship QA checklist

- [ ] Style tile and tokens match the brief
- [ ] All component states exist (hover, focus, active, disabled, loading, error, empty)
- [ ] 360, 768, 1280 and 1920 px layouts checked, no horizontal scroll
- [ ] Keyboard-only run-through of every flow
- [ ] Screen reader spot check on forms and dynamic regions
- [ ] Contrast table verified with the script
- [ ] Reduced-motion mode checked
- [ ] Every flow has its loading, empty, error, success and disabled states built and reviewed
- [ ] Forms label every field, set input types and autocomplete, prevent duplicate submits and explain errors next to the field
- [ ] Consequential actions offer undo or confirmation
- [ ] Hit areas at least 44 px with no dead gaps
- [ ] Icon-only controls have accessible names
- [ ] Tabular numerals on money, times and counters
- [ ] Tested on a real iPhone and a real Android phone
- [ ] Lighthouse mobile run and noted
- [ ] No console errors, no layout shift on load
- [ ] Real content in every state, no placeholder text
- [ ] Open Graph image and favicon set when the project is public
- [ ] Dependencies pinned, lockfile committed, README has run, build and deploy steps
- [ ] Deployed URL confirmed live

### Handover and git commands

Give the owner exact commands for their machine. On Windows, use PowerShell and say which folder to run them in. Template:

## Part 5: Raising the ambition of a request

Adapted from Felix Rieseberg, "How to be more ambitious: A tutorial for humans with models" (felixrieseberg.com, 13 October 2026). The article describes four kinds of ambition: speed, altitude, depth and range. Speed is skipped here because it needs no technique. The examples below are frontend versions written for this playbook.

Run this pass once after understanding the task (workflow step 2) and again before calling a draft done. Anything it produces is **Proposed** until the owner says yes. The brief and the owner's taste still win, so raising ambition never widens scope silently.

### When to apply and when to skip

Apply it when the request is a task with a bigger outcome behind it (restyle a page, fix a bug in a flow, build a component), when the first draft looks like what any similar page would get, or when the owner says the result feels too safe.

Skip it for small direct edits (a typo, a color swap, a version bump), when the brief fixes the scope, and for taste calls. Altitude works best when there is an outcome to reach. It works worst where the answer is a matter of taste.

### Altitude: ask for the outcome, not the task

Ask what should happen next and what the goal beyond the goal is.

| Task | Outcome | System |
|---|---|---|
| Fix the overflow on the pricing page | The pricing page has no layout break at 360, 768, 1280 and 1920 px | Every key route is checked at those widths before each push |
| Restyle this card | A first-time visitor finds the main action in under five seconds | The design system rejects raw hex and off-scale spacing by check, not by review |
| Add a loading spinner | Every async flow has real loading, empty, error and success states | A switch forces failures so the states stay testable |

A useful tell: if the work would normally need a meeting to decide what to do, the request is probably pitched too low.

Prerequisite from the article: before handing over an outcome, make sure the agent can reach what it needs to check it. For frontend work that means it can build the project, serve the production build, take screenshots, read the console and read the repo history. If one of those is missing, say so and ask for it or work around it.

Ladder to climb one rung at a time:

1. Ask what changed, why, and what to do about it, with all the real material attached.
2. Ask for the few most urgent decisions, each with arguments for and against.
3. Ask for a better process than the one the task assumes, and for evidence from the project's own history that it would have caught problems sooner.

### Depth: do it the way the best people in the field do it

Depth means one level further down, not a bigger task.

- **Use the instruments the professionals use.** Asking a model to act like an expert often changes its vocabulary and not its method. Insist on the method: a real browser instead of a described one, the contrast script instead of eyeballing, Figma variables instead of guessed values, Lighthouse instead of a feeling about speed.
- **Start from the rawest material.** The Figma file, not a screenshot of it. The production build, not the dev server. Real content, not a summary of it.
- **Set a specific, hard target and state it as reachable.** "Make it fast" gets less than "LCP under 1.5 s on a mid-range phone". Goal-setting research summarized in the article found that specific hard goals beat "do your best". Mark any target not in the brief as Proposed.
- **Try to disprove what everyone believes.** Before acting on "the layout feels cramped" or "users miss the button", try to reproduce the belief from raw evidence: measured font sizes, spacing counts, hit areas, a keyboard run-through. Report what holds and what does not.
- **Look for what nobody asked about.** Once inside the material, look for blind spots: a state with no design, a flow with no error path, a dependency loaded twice.
- **Use an outside judge.** Do not grade your own output. Use something that returns a result: typecheck, build, `scripts/contrast.py`, `scripts/check_page.py`, Lighthouse, a Playwright flow, a real device, the owner. Say which one was used.

A reusable request for this, in the playbook's own words: before rewriting the task, state what a top professional would do that was not asked for, name the rawest material they would start from, name their methods and tools, and name what other than the agent or the owner would show the result is right. Then rewrite the task to ask for exactly that.

### Range: bring in the fields the task does not name

Range means looking at the work from more fields than would once have been affordable.

- **Replace the nouns with verbs.** "A landing page" is a noun. "Getting a skeptical stranger to trust a studio and write to it in under a minute" is a verb, and it points at copywriting, proof, performance and trust signals.
- **Assemble the crew.** For an interface, a plausible crew is an art director, a copy editor, a motion designer, an accessibility auditor and a performance engineer. For a red team, a first-time visitor who does not trust the page, a screen reader user, and someone on a slow phone.
- **Use fields for their methods, not their voices.** Do not tell the agent to write like a copy editor. Tell it to do what a copy editor does: cut, read aloud, check every claim against the product. Role play makes a transcript stranger and the result no better.
- **Give the agent a computer and the data.** Range needs tools it can run and material it can read. If it only has chat, it will role play.

### When the ambition stalls

The article ties unambitious requests to self-efficacy: people attempt less when they do not believe it is possible. Three documented levers, in frontend terms:

- **Specific hard goals.** Replace "improve performance" with a number.
- **Seeing it done.** Study three real products that already do the hard thing before settling on a pattern (this is what Part 1, Process pattern research is for).
- **Permission to fail.** Try the bold version first on a throwaway branch. Keeping it or dropping it is the owner's call.

## Part 6: Figma to shadcn: build with shadcn, look like the Figma

Owner instruction: use shadcn components, but match the Figma styling as closely as possible.

The split: **shadcn supplies structure and behavior** (Radix primitives, keyboard model, focus handling, ARIA). **Figma supplies appearance** (color, type, spacing, radius, shadow, state styling). Where the two meet, edit the component files so they look like the Figma. Do not leave them looking like shadcn defaults, and do not rebuild the behavior by hand.

### Steps

1. **Read the Figma first.** List the frames, components, variants and the variables or styles for color, type, radius, shadow and spacing. If a Figma connector is available in the session, use it and say so. If it is not, work from exports or screenshots, label every measured value an estimate, and sample colors before they become tokens. Never claim Figma data was read when it was not.
2. **Turn Figma values into tokens.** Figma variable names become primitives. Roles (ground, surface, ink, accent, line) become semantic tokens. Components use semantic tokens only. Rules are in Part 2, Foundations.
3. **Match each Figma component to a primitive.** Dialog, sheet, select, tabs, accordion, tooltip, toast, checkbox, switch, radio and form fields usually map to a shadcn component. If nothing fits, build it custom and record why (Part 4, Build and verify, reuse policy).
4. **Restyle the copied shadcn files.** They live in the project, so edit them. Change variants (with `cva` where the project uses it), sizes, radius and states to the Figma values using the project's token classes. Map shadcn variables (`--background`, `--primary`, `--radius` and the rest) onto semantic tokens. Avoid `!important`, wrapper CSS that fights the component, and per-use class overrides that repeat. On a Tailwind v4 project that reset the default scales, replace classes such as `text-sm` and `rounded-md` in the copied files first.
5. **Keep the behavior.** Leave the keyboard model, focus management, `aria-*` and portal behavior alone. A visible focus ring stays, restyled to the palette.
6. **Fill the states Figma does not show.** Most Figma files show default and sometimes hover. Focus, active, disabled, loading, error and empty usually have no frame. Design them from the token system and list them as Proposed until the owner confirms.
7. **Compare against the frame.** Render the component at the frame's width and set it beside the Figma frame. Check computed styles (font size, line height, padding, radius, color, shadow) against the Figma values. Report each difference with a reason or fix it.
8. **Record it.** In the component spec, name the primitive used, the Figma frame or node link, and the deviations.

### Where Figma and the accessibility floor disagree

Figma files often contain muted text under 4.5:1, targets under 44 px, or inputs under 16 px. Do not copy these silently and do not override them silently. Flag the issue, give the measured value, and propose the smallest change that keeps the intended look (a slightly darker muted ink, extra padding that enlarges the hit area without changing the visible size). List it under Proposed. The owner decides.

### Done when

- The component is built on a primitive, or the reason it is custom is written down.
- Computed styles match the Figma values, or each difference is listed.
- Every state exists and has been looked at, not only default and hover.
- The component works with the keyboard alone.
- No raw hex, no arbitrary values, no leftover shadcn default look.

### Pitfalls

- On Windows, `npx` based shadcn commands can fail. Install the packages directly and add the component files by hand.
- shadcn components merge classes with `tailwind-merge`. Custom token names need to be registered there or they will be treated as conflicts and dropped.
- A visual match in a screenshot does not prove the hover, focus and pressed states match. Drive them in a real browser.

## Part 7: Motion review: use Emil Kowalski's skill for the animation pass

Owner instruction: use Emil Kowalski's design engineering skill to review and refine the animations.

Emil Kowalski publishes agent skills on animation and interface polish. His site (emilkowal.ski/skill) gives the install command `npx skills add emilkowalski/skill`. Public listings of the repository name three skills: `emil-design-eng` (the main skill, mostly animation plus some design advice), `review-animations` (a strict review of animation code) and `improve-animations` (an audit of every animation in a codebase with prioritized plans). Check the installed skill list for the exact names in the current session, because they may change. If the install fails, check the repository name on his site, since listings spell it two ways.

The Playbook does not copy his skill. It points to it.

### When to run the pass

After the motion is built and before verification (workflow step 7). Also when the owner asks for animation to be reviewed or refined.

### Procedure

1. **List every animation.** Name each one: what triggers it, what moves, duration, easing, and whether it runs on a frequent or a rare action.
2. **Check whether the skill is available.** Look at the installed skills.
   - If it is available, run it as the reviewer over that list and the code. Use the output format it defines. If it defines none, ask for findings as a table of before, after and why.
   - If it is not available, say so in one line, offer the install command, and review against the motion rules in Part 2, Foundations instead. Never say his skill was used when it was not.
3. **Refine.** Apply the findings in small commits. Change one animation at a time so a regression can be traced.
4. **Check the floor.** Reduced motion is respected, only transform and opacity animate on large areas, nothing traps input mid-transition, and no animation carries the only copy of information.
5. **Hand over feel to the owner.** A sandbox run shows the code runs and respects reduced motion. Whether it feels right is confirmed on a real device by the owner.

### Which rule wins

Proposed order, to be confirmed by the owner:

1. The brief and the owner's stated taste.
2. The specific values and verdicts from the reviewer skill when it ran.
3. The Playbook's duration ladder and defaults in Part 2, Foundations.

Where the reviewer's numbers are tighter than the ladder, use the tighter numbers for routine interface transitions and keep the ladder's longer steps for the one orchestrated moment per view.

### What to ask the reviewer for

- A verdict per animation, with a keep, change or remove call.
- For each change: the current value, the proposed value and the reason.
- Anything that animates too often to deserve animation at all.

## Part 8: Capture the workflow as a reusable skill

Owner instruction: turn the workflow you just completed into a reusable skill for future tasks.

### When

- The owner asks for it.
- A multi-step task has just finished and the same task is likely to come back (auditing a repo, restyling from a board, a Figma to shadcn build, a pitch mockup, a case study).
- The same workflow shows up a second time. Propose capturing it then. Do not save anything without the owner's yes.

### Procedure

1. **Replay what happened, in order.** Steps, commands, files touched, decisions, dead ends and what fixed them. Work from the conversation and the repo history, not from memory of how it felt.
2. **Separate the procedure from the specifics.** Keep what would be true next time. Strip project names, client names, URLs, keys, personal data and one-off values. Nothing private goes into a skill file, because skill files get pushed to repos.
3. **Write the skill body.** Inputs needed, steps in order, checks that prove each step worked, outputs, and the failures actually met with the fix for each. Leave out the story of the session.
4. **Write the description for triggering.** It says what the skill does and when to use it, including the loose phrasings an owner would really type ("make this look better", "review my repo").
5. **Decide where it lives.** A step in the design and frontend pipeline becomes a section or reference file in this playbook. A workflow with different triggers (cold outreach, case study writing) becomes its own skill.
6. **Keep it small.** Body under about 500 lines. Long detail goes in `references/`. A command run the same way every time becomes a script.
7. **Test it once.** Run it on a fresh task or replay the old one with only the skill as guidance. Fix what the run exposes. If a skill-creation skill is available in the session, use it for this step.
8. **Owner confirms** before it is saved or pushed. Commit with a message that describes the change. No co-author trailers.

### Skeleton

```
---
name: short-kebab-name
description: What it does. Use when <situations and phrasings>.
---

# Title

## Inputs
## Steps
## Checks
## Outputs
## Failures seen and fixes
```

### Quality bar

- Someone who was not in the session could follow it.
- Every step has a check or a visible result.
- The description would trigger on the owner's real phrasings and would not trigger on neighboring tasks.
- Follows Part 9, Writing.

## Part 9: Writing rules

These are the owner's preferences and apply to all copy: interface text, project descriptions, case studies, cold outreach, commit messages and READMEs.

### Rules

- No em dashes. Use a comma, colon, parentheses or a new sentence.
- No "not just X, but also Y" constructions or close variants.
- Plain and factual. Say what the thing is and what it does.
- No AI cadence: no stacked rhetorical triplets, no dramatic one-line paragraphs, no filler transitions.
- No rule-of-three lists unless there are exactly three things.
- No meta-narration ("here is a breakdown of", "let's dive in").
- Project and case study descriptions never open with "I built" or "I developed".
- Sentence case, plain verbs, active voice.
- Each written element does one job.
- Do not credit Claude as co-author or contributor on repos or commits. No `Co-Authored-By` trailers.

### Interface copy

- A button says exactly what happens ("Save changes", "Start a shared space"). The same action keeps the same name through the whole flow.
- Errors say what went wrong and how to fix it. They do not apologize and are never vague.
- Empty states invite an action.
- Say what a calculation includes. A number users act on needs a short "how this is worked out".
- State limits honestly: where data is stored, what the product does not do, what is only an example.
- Defaults unless the brief says otherwise: US English, USD, 12-hour times.

### Voice

Each project defines its voice in the brief with Do and Don't examples. A casual, young-audience voice is still specific and plain: short sentences, concrete situations, humor only where it is earned.

Before and after:

- "Your money. Your people. Your plan." becomes "Split costs with your people. Budget on your own."
- "No transactions yet. Add income or an expense to start tracking your money." becomes "Nothing here yet. Add what you spent today."

### Cold outreach

A cold email states concrete usefulness to the specific recipient. A paragraph about the sender's background does not do that. Lead with what the recipient gains, and show one piece of evidence that is relevant to them.

### Content

Real, specific content in every state. No lorem ipsum. Include the unglamorous parts: FAQs, policies, error and empty states.

### Conditional guidance

Apply these only when the stack or feature calls for them.

- **Theme switching in Next.js.** `next-themes` can switch themes without a flash. Suppress transitions during the switch so they do not fire across the whole interface.
- **Authentication redirects.** Prefer server-side handling to avoid a visible client-side URL change.
- **Video autoplay on iOS.** Use `muted` and `playsinline`. Pause or unmount offscreen video.
- **SVG favicons.** Can adapt to light and dark with `prefers-color-scheme`.
- **Nested menus.** Account for pointer travel so a submenu does not close when the pointer crosses a small gap.
- **Menu opening events.** Opening on `mousedown` can feel immediate, but check it against keyboard behavior, click semantics and accessibility before using it.
- **Keyboard shortcuts.** Implement deletion shortcuts such as Cmd+Backspace only when they are expected, discoverable and safe.
- **Gradient text.** Make sure selected text stays readable.
- **Font rendering.** `-webkit-font-smoothing: antialiased` and `text-rendering: optimizeLegibility` are rendering choices, not universal fixes.
- **Smooth scrolling.** Use it for in-page navigation only when it helps, with a scroll offset for fixed headers.
- **Glow and blur effects.** Scaled or blurred filled rectangles can show banding. A radial gradient is often a better fit.
- **High-frequency values.** Direct DOM updates through refs can avoid excess React renders. Measure first and keep React in charge of structure.
- **Adaptive behavior.** Reduce expensive effects on constrained devices or networks when it improves the experience.
- **Browser and platform quirks.** Focus-ring details and platform gestures change. Check current support and test on the target platforms before relying on an old caveat.

## Appendix, scripts

Save each file to a `scripts/` folder and run it as its header describes.

### scripts/contrast.py

```python
#!/usr/bin/env python3
"""Contrast ratios for color pairs, with WCAG 2.1 AA verdicts.

Usage:
  python contrast.py "#1a1a1a:#ffffff" "#767676:#ffffff"
      Each argument is foreground:background. Hex only (3 or 6 digits).

  python contrast.py --palette palette.json
      Tests every text color on every surface. Format:
      {
        "text":     {"ink": "#14110f", "muted": "#5c554d"},
        "surfaces": {"ground": "#fbf8f3", "card": "#ffffff", "tint": "#efe6d8"}
      }
      Add "ui": {"line": "#8a8178", "focus": "#3b2fd1"} to also test UI
      boundaries and focus rings against the surfaces (3:1 needed).

Thresholds (WCAG 2.1 AA):
  body text 4.5, large text 3.0 (about 24px, or 19px bold), UI boundaries 3.0.

Exit code is 1 when any body-text pair fails, so it can run in a check script.
Hex values read from images are estimates. Sample them before trusting a result.
"""
import json
import sys


def parse_hex(value):
    v = value.strip().lstrip("#")
    if len(v) == 3:
        v = "".join(ch * 2 for ch in v)
    if len(v) != 6:
        raise ValueError(f"not a hex color: {value!r}")
    return tuple(int(v[i:i + 2], 16) for i in (0, 2, 4))


def channel(c):
    c = c / 255
    return c / 12.92 if c <= 0.03928 else ((c + 0.055) / 1.055) ** 2.4


def luminance(rgb):
    r, g, b = (channel(x) for x in rgb)
    return 0.2126 * r + 0.7152 * g + 0.0722 * b


def ratio(fg, bg):
    l1, l2 = luminance(parse_hex(fg)), luminance(parse_hex(bg))
    hi, lo = max(l1, l2), min(l1, l2)
    return (hi + 0.05) / (lo + 0.05)


def verdict(r):
    return {
        "body": "pass" if r >= 4.5 else "FAIL",
        "large": "pass" if r >= 3.0 else "FAIL",
        "ui": "pass" if r >= 3.0 else "FAIL",
    }


def row(label, fg, bg):
    r = ratio(fg, bg)
    v = verdict(r)
    print(f"{label:<34} {fg:<9} on {bg:<9} {r:5.2f}:1  body {v['body']:<4}  large {v['large']:<4}  ui {v['ui']:<4}")
    return r


def main(argv):
    if not argv or argv[0] in ("-h", "--help"):
        print(__doc__)
        return 0

    failed = False

    if argv[0] == "--palette":
        with open(argv[1], encoding="utf-8") as fh:
            palette = json.load(fh)
        surfaces = palette.get("surfaces", {})
        print("Text on surfaces")
        for tname, tval in palette.get("text", {}).items():
            for sname, sval in surfaces.items():
                r = row(f"{tname} on {sname}", tval, sval)
                if r < 4.5:
                    failed = True
        if palette.get("ui"):
            print("\nUI boundaries and focus on surfaces (3:1)")
            for uname, uval in palette["ui"].items():
                for sname, sval in surfaces.items():
                    row(f"{uname} on {sname}", uval, sval)
    else:
        for pair in argv:
            if ":" not in pair:
                print(f"skip {pair!r}: use foreground:background", file=sys.stderr)
                continue
            fg, bg = pair.split(":", 1)
            r = row(pair, fg, bg)
            if r < 4.5:
                failed = True

    return 1 if failed else 0
```

```python
#!/usr/bin/env python3
"""Open a URL at several widths, take screenshots and report common problems.

Setup (once):
  pip install playwright
  python -m playwright install chromium

Usage:
  python check_page.py http://localhost:4173 [--widths 360 768 1280 1920]
                       [--out shots] [--wait 800] [--path-label home]

For each width it saves a full-page and a viewport screenshot, then reports:
  - horizontal overflow
  - console errors and uncaught page errors
  - text under 12px
  - interactive elements under 44 by 44 px
  - buttons, links and form controls with no accessible name
  - images with no alt attribute

What this does and does not show: it shows the page is well-formed and what the
code does in headless Chromium. It does not show how the page feels on a real
phone. Fixed elements appear mid-page in full-page shots, so look at the
viewport shots for bottom navigation. Web fonts may not load in a sandbox.

Exit code is 1 when any finding is reported.
"""
import argparse
import json
import os
import sys

from playwright.sync_api import sync_playwright

PROBE = r"""
() => {
  const out = { tinyText: [], smallTargets: [], unnamed: [], noAlt: [], overflow: null };
  const de = document.documentElement;
  out.overflow = de.scrollWidth > de.clientWidth + 1
    ? { scrollWidth: de.scrollWidth, clientWidth: de.clientWidth } : null;

  const visible = (el) => {
    const r = el.getBoundingClientRect();
    const s = getComputedStyle(el);
    return r.width > 0 && r.height > 0 && s.visibility !== 'hidden' && s.display !== 'none';
  };
  const label = (el) => {
    const tag = el.tagName.toLowerCase();
    const id = el.id ? '#' + el.id : '';
    const cls = (el.className && typeof el.className === 'string')
      ? '.' + el.className.trim().split(/\s+/).slice(0, 2).join('.') : '';
    const text = (el.textContent || '').trim().replace(/\s+/g, ' ').slice(0, 30);
    return tag + id + cls + (text ? ` "${text}"` : '');
  };

  // Text under 12px: check elements that own a non-empty text node.
  const walker = document.createTreeWalker(document.body, NodeFilter.SHOW_TEXT);
  const seen = new Set();
  while (walker.nextNode()) {
    const n = walker.currentNode;
    if (!n.nodeValue.trim()) continue;
    const el = n.parentElement;
    if (!el || seen.has(el) || !visible(el)) continue;
    seen.add(el);
    const size = parseFloat(getComputedStyle(el).fontSize);
    if (size < 12) out.tinyText.push({ el: label(el), size });
  }

  // Interactive elements.
  const sel = 'a[href], button, input:not([type=hidden]), select, textarea, [role=button], [role=link], [role=tab], [role=checkbox], [role=switch], [tabindex]:not([tabindex="-1"])';
  document.querySelectorAll(sel).forEach((el) => {
    if (!visible(el)) return;
    const r = el.getBoundingClientRect();
    // Inline links inside running text are exempt from the target size check.
    const inline = el.tagName === 'A' && getComputedStyle(el).display === 'inline';
    if (!inline && (r.width < 44 || r.height < 44)) {
      out.smallTargets.push({ el: label(el), w: Math.round(r.width), h: Math.round(r.height) });
    }
    const aria = el.getAttribute('aria-label');
    const labelledby = el.getAttribute('aria-labelledby');
    const title = el.getAttribute('title');
    const imgAlt = el.querySelector('img[alt]:not([alt=""])');
    const hasLabelEl = el.id && document.querySelector(`label[for="${CSS.escape(el.id)}"]`);
    const wrapped = el.closest('label');
    const text = (el.innerText || el.value || '').trim();
    const isInput = ['INPUT', 'SELECT', 'TEXTAREA'].includes(el.tagName);
    const named = aria || labelledby || title || imgAlt || hasLabelEl || wrapped || (!isInput && text);
    if (!named) out.unnamed.push(label(el));
  });

  document.querySelectorAll('img').forEach((img) => {
    if (!img.hasAttribute('alt') && visible(img)) {
      out.noAlt.push((img.getAttribute('src') || '').slice(0, 60));
    }
  });
  return out;
}
"""


def main():
    ap = argparse.ArgumentParser(description=__doc__, formatter_class=argparse.RawDescriptionHelpFormatter)
    ap.add_argument("url")
    ap.add_argument("--widths", type=int, nargs="+", default=[360, 768, 1280, 1920])
    ap.add_argument("--out", default="shots")
    ap.add_argument("--wait", type=int, default=800, help="ms to wait after load")
    ap.add_argument("--path-label", default="page", help="prefix for screenshot names")
    args = ap.parse_args()

    os.makedirs(args.out, exist_ok=True)
    findings = 0
    report = {}

    with sync_playwright() as p:
        browser = p.chromium.launch()
        for w in args.widths:
            ctx = browser.new_context(viewport={"width": w, "height": 900})
            page = ctx.new_page()
            errors = []
            page.on("console", lambda m, errors=errors: errors.append(f"console.{m.type}: {m.text}") if m.type == "error" else None)
            page.on("pageerror", lambda e, errors=errors: errors.append(f"pageerror: {e}"))
            page.goto(args.url, wait_until="networkidle")
            page.wait_for_timeout(args.wait)
            base = os.path.join(args.out, f"{args.path_label}-{w}")
            page.screenshot(path=base + "-full.png", full_page=True)
            page.screenshot(path=base + "-viewport.png")
            probe = page.evaluate(PROBE)
            probe["consoleErrors"] = errors
            report[w] = probe
            ctx.close()
        browser.close()

    for w, r in report.items():
        print(f"\n== {w}px ==")
        checks = [
            ("Horizontal overflow", [r["overflow"]] if r["overflow"] else []),
            ("Console and page errors", r["consoleErrors"]),
            ("Text under 12px", r["tinyText"]),
            ("Targets under 44x44", r["smallTargets"]),
            ("Controls with no accessible name", r["unnamed"]),
            ("Images with no alt attribute", r["noAlt"]),
        ]
        for name, items in checks:
            if not items:
                print(f"  ok    {name}")
                continue
            findings += len(items)
            print(f"  FOUND {name}: {len(items)}")
            for item in items[:8]:
                print(f"        {json.dumps(item) if not isinstance(item, str) else item}")
            if len(items) > 8:
                print(f"        ... {len(items) - 8} more")

    print(f"\nScreenshots in {args.out}/. Findings: {findings}")
    sys.exit(1 if findings else 0)


if __name__ == "__main__":
    main()
```
